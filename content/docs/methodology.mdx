---
title: Methodology
description: How work moves through Vatras, from establishing a project to learning from what was built.
---

A methodology gives the work a shape. It describes where work tends to
go, while primitives provide the moves available at any point and flows
combine those moves into larger pieces of work.

## The loop

```text
Establish
    ↓
Understand
    ↓
Decide
    ↓
Plan
    ↓
Build
    ↓
Verify
    ↓
Feed back
    │
    └────→ Persistent context ──→ next pass
```

The return is the important part. A pass should leave the project better
informed than it was before. What is learned during the work becomes part
of the context so the next pass does not start from the same uncertainty.

The stages describe the usual direction of work. They are not a sequence
that every task must follow.

## The stages

**Establish** puts the project's working surface in place: the
[**agent entry point**](/docs/context/agent-entry-point), its adapters, and
the root of the [**Context Architecture**](/docs/context/context-architecture).
It normally happens once per repository.

**Understand** builds a model of the project and tests that model. Read
what exists, form an understanding, challenge it, and investigate what
the challenge exposes. Terminology settles along the way and is recorded
in the project.

**Decide** records choices that would be costly to reverse, together with
the reasoning behind them. Decisions that are not recorded have to be
re-derived later.

**Plan** turns an intended change into concrete work. The plan is an
artefact; where it lives is not prescribed by Vatras.

**Build** implements the plan using the project's existing vocabulary,
context, and decisions.

**Verify** asks whether what was built is what was intended. That is
different from asking whether it runs.

**Feed back** captures what the work revealed and puts it where it can
inform the next pass. A failure that produces no change to the project
context is likely to be repeated.

## Stages, primitives, and flows

These describe different dimensions of the work.

| Concept | Describes |
|---|---|
| **Stage** | Where the work is in the methodology |
| **Primitive** | A basic operation that can be performed at any point |
| **Flow** | A combination of primitives into a larger piece of work |
| **Skill** | The instructions used to perform a capability |

A stage does not restrict which primitives can be used. A flow can cross
stage boundaries when that is useful.

For example, challenging an understanding is not reserved for
**Understand**. It can happen during planning, implementation, or
verification when new information makes the existing understanding
questionable.

## What is built so far

**Establish** exists as `vatras:init`.

**Understand** is partly implemented. Its operations have names, and
[**Vocabulary**](/docs/context/vocabulary) has a skill behind it.

The remaining stages are defined by the methodology but are not yet
implemented. They are named here because they describe the intended
shape of the complete loop, not because every stage is currently
available as a Vatras skill.
