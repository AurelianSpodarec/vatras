---
title: Idea Inbox
description: Where a thought goes when it is not ready to be used.
---

Most project knowledge exists to be used. An idea inbox exists so that a
thought can be put down without being used at all.

`IDEAS.md` sits at the root of the repository and holds anything not yet worth
deciding: half-formed thoughts, questions with no owner, directions that might
matter later.

Nothing reads it.

## How an idea is created

Most arrive the obvious way — you notice something and write it down before it
derails what you were doing.

Two others matter more than they look:

```text
split       one idea turns out to be two
produced    asking for alternatives returns several
```

Ideas can be **output** as well as input. So the inbox is not only where the
flow starts; it is somewhere the flow puts things.

## Working an idea

Every entry has an id, and an operation is aimed at one: `0023`.

| Operation | Takes | Produces | Skill |
| --------- | ----- | -------- | ----- |
| **Capture** | a thought | an entry | `vatras:idea` |
| **Critique** | an entry | objections, hidden assumptions, alternatives | `skill:critique` |
| **Investigate** | an entry and its open questions | findings, constraints | `skill:investigate` |
| **Iterate** | an entry | a sharper entry | `skill:iterate` |

Each stands alone. An idea can be critiqued without being investigated, or
sharpened without being critiqued.

## The cycle

```text
capture
   │
   ↓
 ┌──────────────────────────┐
 │  critique                │   what is assumed, what breaks it
 │     ↓                    │
 │  investigate             │   can it be done, what constrains it
 │     ↓                    │
 │  iterate ────────────────┘   rewrite it knowing what you now know
 │     │
 └─────↓
    resolve                     becomes work · merges · is dropped
```

A sharper idea is often worth critiquing again, which is why it loops.

Most entries never enter the cycle at all. That is the design working: an inbox
where every entry must be processed is a queue, and a queue creates obligation.

Running the three as one pass is a flow rather than an operation —
`skill:develop`.

## What exists so far

Only capture. `vatras:idea` is built; everything marked `skill:` is named
because the cycle is incomplete without it, not because it can be used.

Whether these operations belong to ideas alone, or are the same operations
aimed at a smaller subject, is deliberately left open.

## Why it is excluded

An agent reading *"idea: maybe this should be event-sourced"* has no way to
tell a stray thought from a settled decision. Both are sentences in a file in
the repository.

Put unevaluated ideas into loaded context and they quietly become assumptions.
The agent starts reasoning from them, and nobody notices, because nobody
decided anything.

Excluding the file is what makes it safe to write in. Capture commits to
nothing, so anything can be captured — which is why the inbox occupies its own
position in how context is loaded:

```text
Always        Vocabulary
When relevant Decisions, research, requirements
Never         Ideas
```

## What does not belong here

An inbox works because entries cost nothing to add and nothing to leave. It
stops working when it starts carrying weight:

- decisions — those belong where they can be found and cited
- plans — an idea that has become work is no longer an idea
- terminology — a term that has settled belongs in the
  [vocabulary](/docs/context/vocabulary)
- anything an agent needs in order to do its job

If something in the inbox turns out to matter, it will resurface through the
work. Then it moves somewhere that is read.
